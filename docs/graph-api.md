# The module graph API (design)

How origine will load, link, cache and snapshot modules, replacing the `main`/`importMap`/`loader`/`transformers`/`origineNamespace` options of `api.scope.create`. This page is the design reference. Reference documentation for what exists is [src/js/docs/graph.md](../src/js/docs/graph.md); the rules every name here follows are in [api-guidelines.md](api-guidelines.md).

## Status

All of it is implemented except what the last row lists. Tests: `src/tests/managed/api.zig` (the `graph:` tests), `shared_link.zig`, `async_resolve.zig`; types: `types/std/graph.d.ts`, `types/graph.d.ts`, `types/context.d.ts`.

| Part | State |
|---|---|
| `origine:@std/graph/*`: sources, recipes, resolver layers, `ImportHandler` (hooks, maker, cache), `ImportHook` verdicts, providers, caches; `origine:@std/transformer/oxc` descriptors | JS validation and JS class instances, snapshot-safe (`src/js/std/graph/`). |
| `api.graph` (`root`, `create`), `graph.declare(recipe)`, `ModuleReference` (an inert ticket); the graph's `declare`, `load`, `requests`, `evaluate`, `exports`, `release` | `src/api/graph.zig`, `src/api/context.zig`, `src/js/glue/graph.js`. |
| `api.context` (`create`, `import`, `references`, `close`, preload) | Replaces `api.scope`, which is gone. |
| Async or layered resolution in `ModuleMap` | `Resolver.resolve_async`, `Runtime.completeResolve` (`src/managed/module_map.zig`). |
| Native plans | A chain runs natively until it reaches a JS function and goes back to native after it; see Native plans. |

A handler names its cache, a recipe may override it for its module. |
| `Snapshot.prepare` and baked contexts (multi-context `init_snapshot`) | Later, and the module graph's: the `api.isolate` snapshot step stays single-context. |
| Source and defer phases | Not implemented; `ModuleImportPhase` names them, only `Evaluation` works. |

## Deviations from the first design

What the implementation does differently from the proposal this page started as:

1. **An `ImportCache` object names a table of modules.** Each context keeps the tables of the cache objects its handlers use in its `ModuleMap` (the module's table number is part of its key), so one id imported through two cache objects is two modules, also inside one context; handlers made with the same object share one table. **Contexts that use the same `ImportCache` object share its modules**, with no option: the first context to import an id is its home (it compiles, instantiates and evaluates the module), and every other context gets that module through the `'shared'` link machinery (live bindings, the same objects, the module runs once). A context that asks while the home is still loading or evaluating waits for it (`Loader.poll`); a module that failed in its home is not shared, so the asking context loads one of its own. Separate caches are separate `ImportCache` objects. `retain` is per table, and `size`, `delete(id)` and `clear()` are on the object (no `cache.in(ctx)`): `size` counts the modules the table holds (a shared one once, in its home), `delete(id)` and `clear()` forget them in every context of this realm that holds them. `retain: 'used'` counts users across contexts: a context that links a module pins it in its home, and releases the pin when its own entry is released. When the home context closes, the contexts that used its modules drop them (and what imported them), and their next import evaluates a new module there (the first one to ask becomes the new home); a reference they already held stops resolving (`exports()` is `NotFound`). There is no `entries` cap on an `ImportCache`, on purpose (see the checklist row): the table is an identity cache.
2. **Nothing names an fs grant but the thing that reads with it, and the graph holds none.** `fsProvider({ fs, read })`, `json({ fs })`, `ImportHook.accept({ fs })` and `ModuleSource.file(path, { fs })` take `api.fs.requestSync(...)` or `await api.fs.requestAsync(...)`; a grant is an `FsGrant` instance `api.fs` returned (a JS class extending `Handle`): its issuer, kept in a private field only `issuerOf` of the real instance reads, is the native grant the host built (stamped with a V8 private symbol), and the glue takes that issuer from an `FsGrant` and asks the host (natively) whether it is a grant of this realm that is still open, when a handler is taken by a context, when a source is read, when a verdict is answered. A lookalike with every property of a real grant (a copy, a proxy, an object inheriting from one, a clone) has no issuer, so it is `InvalidInput`, so a realm that was handed `api.graph` cannot reach the grants of the realm that gave it. A sync grant is read by the host with its own blocking read inside the load stage. An async grant is read on its io runtime: the context's chain calls the grant's Rust natives (open, read all, close) itself and parks on their promises, so the read completes through `completeLoad` and no JS function runs. Several roots are several providers with `missing: 'skip'`, tried in hook order (the default `'abort'` fails the import with `NotFound`, so nothing reads another root unless the program asked). A source file is read whole: there is no size limit on the graph, so a program that wants one checks the size in a hook of its own and fails the import with `ImportError.other(message)`. `CodeCache.dir({ fs, path })` stays on a sync grant on purpose: V8 asks for a module's cached bytes while it compiles, and a compile cannot wait, so an async-grant `dir` would need a chain step of its own that reads the file before compiling. `CodeCache.custom({ load, store })` is that step today and may use any async io.
3. **`meta` lives on the handler only.** The maker returns `{ import?, transformer? }`.
4. **`ModuleReference.status` has no `instantiated`**: linking happens inside `graph.evaluate`, so a reference goes `declared`, `loaded`, `evaluating` (linking included), `evaluated` or `errored`. `requests[].reference` are one level deep: they are `declared` until `graph.load` is called on them, and `graph.load` works the same on such a dependency (its source was read when it was made), so a program that wants a whole tree calls it level by level. Overlapping loads of one reference share one load.
5. **The origine ceiling** (what `origineProvider` may include) comes from the context's import handler only; the init scope is unrestricted. A hook that names more than that is `PermissionDenied` (`Unsupported` in a context whose handler serves nothing). `origineProvider()` and `origineProvider({ std: true })` mean "whatever that context may import": the host copies the creating context's own set, so the default can never widen it.
6. **A root module is addressed by its name.** `evaluate` and preloads register the source under the module's `name` and import that name, bypassing the resolver; the name must be unused in the context's table (`InvalidInput`).
7. **Errors from JS hooks**: an `ImportError` kind keeps its kind; anything else, `ImportError.other(message)` included, reaches the importing module as an `Error` with `name: message`.
8. **Oxc transformers are JS descriptor instances** (`ts()` returns a `Transformer` with read-only host, kind, transform, and options fields), no longer callable functions.
9. **The graph is the entry point and a `ModuleReference` is an inert ticket.** The proposal had the reference run itself (`recipe.create(graph)`, `ref.load()`, `ref.evaluate(ctx)`, `ref.exports()`, `ref.release()`, `ref.requests`). A handle that can run, read and free a module is a power, so the graph does it: `graph.declare(recipe)`, `graph.load(ref)`, `graph.requests(ref)`, `graph.evaluate(ref, ctx)`, `graph.exports(ref)`, `graph.release(ref)`; the reference keeps `name`, `status` and `context` and has no `Symbol.dispose`. The old methods are removed, with no alias. A reference belongs to one graph (`InvalidInput` from another, another created graph included); `graph.evaluate(ref, ctx)` also needs `ctx` made with that graph; closing a created graph makes its references `StaleHandle`. There is no `graph.import(recipe, ctx)` shorthand: `ctx.import(specifier)` already loads and evaluates.
10. **The graph API does not copy or freeze on the caller's behalf.** The proposal had `ImportHook.link(ref, { mode: 'hardened' | 'shared' })` and a snapshot `ref.exports()`. Now `graph.exports(ref)` is the live module namespace and `ImportHook.link(ref)` links the module itself, with no `mode`; sharing crosses the realm boundary and the docs say so. Handing data over is separate: `ImportHook.exports(values)` builds a synthetic module (the managed layer's `Content.exports`, values neither copied nor frozen), and `snapshot` / `deepFreeze` of `origine:@std/data` copy and freeze any object. `deepFreeze` is the user's `seal`, renamed (the user's decision) because `Object.seal` is not a freeze and `freeze` would clash with `Object.freeze`; `snapshot`'s option takes the same spelling, `deepFreeze`.
11. **`ImportHook.provide` is two verdicts.** `ImportHook.source(source)` goes through the maker, `ImportHook.recipe(recipe)` is final: two semantics, two names.

## Facts that shape the design

1. A `v8::Module` is compiled per isolate but instantiated and evaluated in **one** context. A `ModuleReference` is therefore bound to the first context that evaluates it; the same code in a second context is a second reference made from the same recipe, cheap when sources and code-cache bytes are shared.
2. V8's resolve callback is synchronous, so the static closure is loaded before instantiate. Loading is async-capable (`Loader.load` returns `.pending`); **resolution is not**: `ModuleMap.compile` resolves and fetches each request synchronously, and `Scope.Options` allows one resolver. Layered or async resolution means parking the entry and resuming when the resolver settles.
3. Heap snapshots exist only at isolate boot, and `init_snapshot.Table` has one context today (baked contexts are deferred).
4. Values do not cross realms (`Scope.harden`). **Every user callback (resolver layer, hook, maker, transformer, meta, code-cache store) runs in the creating realm during the async load stage and returns data; natives never call JS during instantiate or evaluate.** `meta` therefore runs when a module is made and its plain-data result becomes `import.meta`. The JS driver waits one microtask before it runs any of them, so none runs on the stack of a child's own `import()` (that call reaches the host synchronously); a hook may create contexts, since it runs from the microtask checkpoint, outside the runtime's scope iteration.
5. `compile` rejects any phase but `Evaluation`, and `instantiateModule` takes no source callback yet.

## The pieces

| Noun | What it is |
|---|---|
| `ModuleSource` | `file(path)` or `text(str)`, an optional `SourceMap`, and a `withTransformer(t)` chain. Immutable data. |
| `ModuleRecipe` | `source`, `import` (an `ImportHandler`), `name`. Immutable; building it reads nothing. |
| `ImportHandler` | The pipeline for a module's imports: `resolver` -> `hooks` -> `maker`, plus `cache` and `meta`. |
| `ModuleGraph` (`api.graph.root`, or what `api.graph.create()` returns) | The table of modules shared by the contexts that use it (and the shared source text, transform output and resolve results). It holds no authority: the fs grants are named by the hooks and sources that read, the code caches by the handlers and recipes that compile. `api.graph.create()` makes one the caller owns. |
| `ModuleReference` | An inert ticket for an entry in a graph's table (a module id), made by `graph.declare(recipe)` or found in `graph.requests(ref)[].reference`. It shows `name`, `status` (`declared`, `loaded`, `evaluating`, `evaluated`, `errored`) and `context`, and can do nothing: the graph that declared it loads, evaluates, reads and frees it. `graph.evaluate(ref, ctx)` binds it to one context. |
| `ImportCache` | The name of a table of modules (id, attributes) -> reference, shared by the contexts that use the object, with `retain`, and the handle to inspect it (`size`, `delete`, `clear`). |
| `Context` (`api.context`) | A realm. Replaces `api.scope`. |

```js
const handler = ImportHandler.make({
  resolver: ImportResolver.layered().layer(relative()).layer(origine()),
  hooks: [
    async resolved => (resolved.id === 'secret' ? ImportHook.reject(ImportError.PermissionDenied) : ImportHook.next()),
    origineProvider({ std: { include: ['text'] } }),     // serves origine:@std/text and nothing else
    fsProvider({ fs: src, read: 'copy' }),               // native, no JS per import
  ],
  maker: MakeRecipe.inherit({ transformer: Transform.byExtension({ '.ts': ts() }) }),
  cache: ImportCache.native({ retain: 'used' }),
});
const mod = graph.declare(ModuleRecipe({ source: ModuleSource.file('./main.ts', { fs: src }), import: handler }));
using ctx = await api.context.create({ import: handler, graph });
await graph.evaluate(mod, ctx);
```

### Hooks and `maker` answer different questions

| | `hooks` | `maker` |
|---|---|---|
| Question | What does this resolved id map to, is it allowed, who supplies it? | Given supplied content, which recipe options apply, and which handler governs its own imports? |
| Shape | ordered; the first verdict that is not `next` wins | one function, runs once, for `source(...)` and `accept()` |
| Output | `next`, `accept`, `source`, `recipe`, `link`, `exports`, `reject` | `{ import?, transformer? }` (options, never a recipe) |

Nearly every provider returns text, and the module it becomes must be made the same way for all providers; without `maker` each provider would rebuild a recipe. Its non-redundant power is choosing a different child handler per module (a no-fs handler for `node_modules/`). `ImportHook.recipe(recipe)` and `ImportHook.link(...)` skip it.

### Transformers

A transformer is a property of a source (`ModuleSource.file(p, { fs }).withTransformer(t)`) and an option of `maker`, with the same meaning. A hook cannot apply one because hooks stop at the first verdict. A function transformer `(source, id) => string | { source, map } | Promise` runs in the creating realm and may be async; the oxc transformers become host descriptors. V8 compiles the post-transform text, so code-cache keys stay correct. Source maps are carried, not applied (no stack remapping).

### `origine:` modules

There is no `origineNamespace` flag. `origine()` only canonicalises `origine:` ids; `origineProvider()`, `origineProvider({ std: true })`, `origineProvider({ std: { include | exclude } })` serve them (the first two: every one the creating context itself may import), bound to the importing context's natives, and can only narrow the creating context's own set. Entries made by the native provider carry a host-origin bit that no JS verdict can set; an `origine:` id without it is `PermissionDenied`, so working-directory files still cannot take the namespace.

### Native plans

`ImportHandler.make` classifies each element: a JS descriptor instance is validated and compiled to a native step; a function is a JS barrier. Consecutive native steps are fused into one plan exposed through the existing managed `Resolver` and `Loader`; a barrier parks the entry, runs in the creating realm during the load stage, and resumes the native steps. A fully native handler never enters JS (`init_loader.zig` is that chain written by hand today), and in a handler that also has functions the host elements still run in Zig: the context's chain (`context.zig`: `advanceResolve`, `advanceHooks`, the maker, `made`) runs them itself and calls the driver once per function it reaches, with the same token until the request completes (`host.driver_calls` counts those calls; tests assert them). `graph.load(reference)` has no request to park, so it runs a handler through a small loop in JS (`resolveInJs`, `loadInJs`) that goes element by element in the same way: a native one in the host, a function in JS. `ImportCache` is native only: it sits behind V8's synchronous link. The cost is visible: `handler.plan` lists every element as native or JS, so a handler whose plan is all native makes no JS pipeline callbacks for its own elements (a handler it names in `MakeRecipe.inherit({ import })` has its own plan); its private JS identity does not grant graph authority.

### Cross-context imports

| Verb | The importer gets | Safety |
|---|---|---|
| `ImportHook.source(source)` | a fresh module of that source in its own context, made through the `maker` | safe |
| `ImportHook.recipe(recipe)` | a fresh module of the recipe in its own context, final (the maker is skipped, the recipe's own handler answers its imports) | safe |
| `ImportHook.link(ref)` | the other context's module itself: live bindings, the other realm's own objects (an alias when `ref` is bound to the importer's own context) | nothing is copied, frozen or wrapped, so this **crosses the realm boundary**: a function the importer calls runs in, and reaches, the exporting realm, and the importer can mutate the exporter's objects; V8 accepts it (spike below) |
| `ImportHook.exports(values)` | one synthetic module whose namespace is `values` (own enumerable string-keyed data properties; `default` allowed), built by the host over its `Content.exports` | nothing is copied or frozen: each value is the caller's own object or function, shared as it is, so the importer reaches whatever the values reach; the realm leak is the caller's and documented. Compose a data hand-over with `snapshot` and `deepFreeze` | an `origine:` id is `PermissionDenied`; it is never bakeable (a synthetic module is not snapshottable) |

`link` takes a reference bound and evaluated in a context (`InvalidInput` for one that is not). There is no `mode`: the graph API does not copy on the caller's behalf, so the one link is the module itself. To give a context data and not the exporter's realm, build a synthetic module of copies: `ImportHook.exports({ config: snapshot(graph.exports(ref).config, { deepFreeze: true }) })` (`snapshot` copies plain data, `deepFreeze: true` also freezes the copy; both are in `origine:@std/data`). A function in the values is still the exporter's, shared as it is, and `snapshot` refuses one.

**Spike result (`src/tests/managed/shared_link.zig`, also exercised end to end by the `graph: link` test).** Two scopes of one isolate: `Module::InstantiateModule` in the importer's context accepts a dependency that was already instantiated and evaluated in the other context. The importer reads live bindings (a counter bumped in A is seen by B's imported binding) and receives A's own objects (their creation context is A's, not B's). So the link ships; it is the documented realm leak, available only to code that holds both the reference and the importer's handler. Node's `vm.Module` refuses this combination by policy; V8 itself does not. Authority is the handle: only code holding both the reference and the importer's handler can write the verdict, and hooks run in the creating realm.

### Caches and lifetime

| | Key -> value | Notes |
|---|---|---|
| `ImportCache` | (id, attributes) -> reference | one table per cache object, shared by every context of the realm that uses it (home context + users); `retain: 'all' \| 'used'` is required |
| `CodeCache` | (id, source hash) -> V8 code-cache bytes | `none`, `memory`, `dir` (`<32 hex digits of BLAKE3(runtime, module kind, source text)>.v8-code-cache` directly in `path` of the sync write grant `fs`: the id is not in the name, so virtual ids and ids with `..` stay inside it; each file holds its source's hash), `custom` (`key` is `{ id, hash }`, the hash being the lowercase hex BLAKE3 digest of the exact text V8 compiles; `load(key, source)` runs once a module's source is final and before it compiles, `store(key, blob)` at `cache.flush()`; the blob is opaque and carries the hash of its source, so one made for another text, a throwing `load` or a non-blob answer is a miss, never an error). A handler's `codeCache` is the default for the modules it makes, a recipe's `codeCache` overrides it (`CodeCache.none` turns it off) |

Artifacts (source, transform output, code-cache bytes) are evictable and bounded. A reference is freed when its table entry, live JS handles and dependents' edges are gone; `delete(key)` is an identity reset (the next import makes a new reference and evaluates again). `'used'` frees unused entries automatically at the price of re-evaluation. A module a context already linked cannot be unloaded from it. Handles are explicit (`release()`, `using`); freeing on GC is a known gap shared with scopes (`WeakRef` and `FinalizationRegistry` exist in a realm, but their instances are not exportable values, and nothing here relies on them).

What the host keeps is bounded by what is live. A context is freed with its scope once it is closed (its record, resolution cache, `import.meta` data, import and preload records). An import handler is freed when a context is freed and no live context, call in flight or `graph.load(reference)` reaches it, and the JS side then drops its record and the closures in it; the same handler object registers again if it is used later. A graph made by `api.graph.create()` is freed after `close()` once the contexts that use it are gone (`api.graph.root` lives as long as the realm). Ids are never reused, so a handle to a freed record is `StaleHandle`. A call into a JS element whose promise never settles keeps a small record until the host is destroyed.

### `api.context`

`api.scope.create` mixes the realm, what it loads and what it runs. The graph takes the second, `graph.evaluate(ref, ctx)` the third; what is left is `api.context.create({ import, graph, preload? })` with `import(specifier)` and `close()`; `graph` is required (no default `api.graph`: a choice with consequences). `api.scope` is replaced outright, no alias. The old call is `fromLoader(loader)` as a hook, `Transform.byExtension(transformers)` in the maker, and `ctx.import(main)`. A child never receives the graph.

## Snapshots

- **Code cache** (works today in the init scope): `CodeCache` over `src/api/init_cache.zig`; `codeCache.flush()` writes what compiled without a usable cache.
- **Baked contexts** (later): N contexts per boot blob, so a child context restores in about 0.2 ms with no parse or evaluation. Needs a multi-context `init_snapshot`; that change belongs to this design, not to `api.isolate`, whose snapshot step stays single-context.
- **Child isolates** (the `api.isolate` design): `api.isolate.Snapshot.create(options)` (with `Snapshot.fromRaw`, `Snapshot.fromOrigineDataBlob`, `.blob()`, `.origineDataBlob(options)`) takes `init: string | ModuleRecipe`, `import: ImportHandler` and `graph?` instead of a specifier and an import map (`importMap` and `meta` are dropped). No graph or grant crosses to a child isolate: its init script decides everything, and the parent controls that by choosing the init script. Only a handler with no JS element in its `plan` (plain data), nor in a handler its maker names, is cloneable, as part of the child's `import` option; one with JS hooks, layers or makers is `Unsupported`, and `handler.plan` names the element.

## Name decisions

- PascalCase for values and variants (`ImportError.NotFound`, `SourceMap.None`), camelCase for functions (`SourceMap.url`, `ImportHook.next`), so a variant with a payload is a function (`ImportError.other(message)`).
- `hooks` for the chain and `ImportHook.*` verdicts, flattened from `Bail.*`: `next`, `accept`, `source`, `recipe`, `link`, `exports`, `reject`.
- Dropped as second ways to one thing: `ImportResolver.custom(fn)` (a layered resolver with a function layer) and `ImportHandler.makeCustom(fn)` (a function layer plus a hook).
- `withTransformer` keeps the `with` prefix the guidelines discourage: it is an immutable builder on data, and the name was chosen by the maintainer. This is the one deliberate exception.
- There is no `ResolveCache`: an answer depends on the referrer (a relative specifier holds for one directory) and resolving through the native layers is already cheap, so a memo would not earn its place. `CodeCache` capacity is `limits.size` (in bytes, said in its doc): the limit is a number you can read. `ImportCache` has no capacity: an identity table that evicted one module while others stayed would hand out two instances of one id (a re-import would evaluate it again, and live bindings and `instanceof` would split), so its only bounds are `retain: 'used'` (frees what nothing holds) and explicit `delete`/`clear`. A cap is sound only on a memo whose entries are derived and recomputable (`CodeCache.memory`); do not add one to `ImportCache`.

## Checklist (api-guidelines.md), by name

Question 1: what the name promises. 2: hidden cost. 3: another way. 4: shed words. 5: errors. All builders throw an `IoError` instance with errno `InvalidInput` and a message for a malformed argument; nothing here touches I/O, so nothing blocks or retains a host resource; factories allocate JS class instances and JS copies input data.

| `origineProvider`, `fsProvider`, `json`, `fromLoader` | providers/hooks | `missing` of `fsProvider` and `json` defaults to `'abort'`, which never reads another root; `'skip'` is the explicit opt-in to the next hook. `fsProvider.read` is required because it chooses a cost: `'mmap'` is the explicit opt-in to V8 reading a large ASCII file in place, where the file must not change while the module lives (truncating it crashes the process). `origineProvider.std` is optional: the default serves everything the creating context itself may import, never more. Authority is the handle: only code that can name the `ImportCache` object (or a handler made with it) can attach it to a context, and there is no option to turn sharing off, you use two objects. `ImportHandler.make` makes its default `ImportCache.native({ retain: 'all' })` once per handler, so **two contexts created from the same handler object share module instances by default**, and a handler per context keeps them apart; `dir` touches the disk when the graph uses it; `custom.load` runs once per module that compiles, in the creating realm, and its failure is a miss | caches are not pluggable in JS except `CodeCache.custom` | `InvalidInput` |
